# eharness 0.5.0 — results of the prior-art review

For: the maintainers and the first production user (BTeams), answering the eight candidate
features of the 0.5 prior-art analysis (items #1–#8; the analysis itself is maintainer-only and
not committed). From: eharness maintainers. Status of this document: written before the 0.5.0
version PR; every item below is merged on `main` unless marked otherwise.

The analysis asked one question per item: is it **generic** (at least two large agent frameworks
ship it, and at least three kinds of products outside a team-management app need it), and if so,
is it core, a plugin, only an example, or application policy? The verdicts below are that
classification, followed by what shipped.

All changes are backward compatible in the 0.x sense: without new configuration, 0.4.x behaviour
is unchanged. The only stored-shape change is `PendingState.v: 2`, written by 0.5 on every
pending state (state without `v` keeps working). Type-level additions that break exhaustive
`switch` statements or `Record<ToolRisk, …>` objects are listed per item and in the changesets.
Peer floors are unchanged: `ai@^7.0.127`, `zod@^3.25.76 || ^4.1.8`, optional `@ai-sdk/mcp@^2.0.66`.
The signature blocks below are summaries; the exact types are in the linked specs and in the
package's `.d.ts`.

## #1 — Park-and-resume (external waits)

**Verdict:** generic, core. Nearly every serious agent framework parks a run on an external
result; they differ only in the execution model (replay versus snapshot). eharness takes the
snapshot-at-the-tool-boundary model, which avoids the replay trap (side effects before an
interrupt running twice).

**Final API**

```text
externalTool({ description, inputSchema, outputSchema?, start?, timeoutMs?, onTimeout?, metadata? }): Tool   // no `execute`
  start(input, { waitId, toolCallId, ctx, abortSignal }) → { correlationId?, payload?, timeoutMs?, timeoutAt?, onTimeout? } | void
session.resolveWait(waitId, { output } | { errorText }, options?)
  → { status: 'continued', run } | { status: 'recorded', remaining } | { status: 'already-resolved' } | { status: 'not-pending' }
session.expireWaits(now?) → { expired: string[]; run? }
session.pendingWaits() → PendingExternal[]
session.respond({ approvals, toolOutputs, externals })
// stop 'tool-pending'; TurnResult.pending.externals[]; SessionEvent { type: 'wait-resolved', waitId, by }
// fixed texts WAIT_TIMED_OUT, WAIT_CANCELLED_NEW_INPUT; inbox item kind 'wait-timeout' (with availableAt)
```

`waitId` is `w_<toolCallId>`. A result is validated against `outputSchema` (`EH_INVALID_INPUT`,
`details.reason: 'invalid-result'`), passes `tool.after` and the output limits, and is recorded
with a compare-and-set: the first result wins, a replay is `already-resolved`. When nothing is
left open, the **same** assistant message continues like a `respond()` continuation (ADR-0012).

**Differences from the proposal**

- **No `resume(runId, results)`.** The unit is the session: the result of one wait is recorded
  by `resolveWait(waitId, …)`, one at a time, from any instance; there is no run id. A batch is
  `respond({ externals })` (trusted server call, not validated against `outputSchema`).
- **A tool without `execute`, not a returned `park()` marker.** A marker would be recorded by AI
  SDK as a real output chunk and the core would have to rewrite chunks, against "chunk order is
  public API". The harness-side `start` runs once per call after the step ended and before the
  pending state is committed (inside the turn, so `ctx.turn` is live).
- **No kind `event`** next to `approval` and `external`: request-declared client tools (#4) and
  external waits share the pending machinery instead.
- **Timeouts have three paths** that all use the same compare-and-set: a timer in the holding
  process (capped at `setTimeout`'s 2^31-1 ms), a durable `wait-timeout` inbox item
  (`availableAt`, any instance) and `expireWaits()` for sweepers. The proposal named only the
  explicit result; the default is `WAIT_TIMED_OUT`, per-wait overridable.
- **Only external results are recorded one by one.** Partial approval answers stay on the
  roadmap.
- **No new hook** for `wait.resolved`; the `wait-resolved` event and `turn.end` cover audit.
- **Versioned pending state:** `PendingState.v: 2` (the OpenAI `$schemaVersion` lesson); no `v`
  is the 0.3 / 0.4 shape, an unknown `v` authorizes nothing.
- Type-level: `InboxItemInput` gains the kind `wait-timeout`, `SessionEvent` gains
  `wait-resolved`, `EH_INVALID_INPUT` gains the reasons `'wrong-kind'` and `'invalid-result'`,
  `HarnessSession` gains three methods (custom implementations must add them).

**What stays app policy:** authenticating the webhook and deciding who may resolve which wait
(the core cannot verify a sender; a browser can never resolve a wait), the correlation map from
your ids to `sessionId` + `waitId`, and the sweeper schedule.

## #2 — Approval classifier guard

**Verdict:** generic, plugin. The hook point (decide before a tool runs) is core and exists
everywhere; an LLM judge is shipped as a separate plugin on top of it. The "only tightens"
principle is made explicit and enforced by construction.

**Final API**

```text
import { approvalGuard } from 'eharness/guard'
approvalGuard({ model, policy?, skipRisks? = ['read'], skipTools?, onlyTools?,
                transcript?: { maxMessages? = 20, maxChars? = 12_000 }, timeoutMs? = 15_000, maxRetries? = 1,
                maxConsecutiveDenials? = 3, cache?: { maxEntries? = 200, ttlMs? } }): HarnessPlugin<'guard'>
// core: the `tool.approve` event gains `transcript(): GuardTranscriptEntry[]`
// warning W_GUARD_UNAVAILABLE; texts GUARD_*; helpers canonicalJson(), verdictKey()
```

The plugin returns `denied` (the reason reaches the model) or `user-approval`, never
`approved`, so with most-restrictive-wins it cannot loosen a policy, a risk rule, a hook or a
grant. The judge sees a restricted view built by the core: user messages and the agent's earlier
tool calls, never tool outputs, assistant text, reasoning or instructions. Read-risk calls skip
the judge; verdicts are cached per session by tool and SHA-256 of the canonical input; the
consecutive-denial breaker escalates to a person; a failing or slow judge fails closed to
`user-approval`; judge usage is charged to the turn (`addUsage`, so the ledger of #3 sees it).

**Differences from the proposal**

- **Verdict set:** the proposal's `allow | ask | deny | rejectWithMessage` collapses to the
  plugin's `denied` (with a reason) and `user-approval`; `allow` is "not applicable" (the rest
  of the chain decides), and there is no `rewrite`.
- **The restricted transcript is built in core** (`transcript()` on the event), not in the plugin:
  the restriction is the security property and must not depend on each plugin. Text projected
  by app code (custom `model` functions, `input.submit` context) and steered input appear as
  user text and are documented as such.
- **Determinism beyond the verdict cache:** AI SDK re-validates approved calls on a `respond()`
  continuation, so the plugin also records its answer per tool call id and returns it first;
  a person's approval of an escalation can never be turned into a denial on re-validation.
- **Judge output** is `Output.object({ decision, reason })` (works with `scriptedModel` and real
  providers); `maxRetries` defaults to 1 (the AI SDK default 2 would triple latency on an outage
  before failing closed). Cache is per session only, never shared across sessions.
- A person's session-wide `always` grant answers guard escalations like any other
  `user-approval` and never overrides a guard denial.
- Type-level: `WarningCode` gains `W_GUARD_UNAVAILABLE`; the `tool.approve` event gains a
  required `transcript` field (code that calls hooks by hand must pass it).

**What stays app policy:** the policy text, which tools to skip, the base approval rules the
guard sits behind, and whether an LLM judge belongs in the product at all (it is probabilistic;
keep deterministic rules as the first line).

## #3 — Cross-session budget ledger

**Verdict:** split. Per-run limits already exist (`budget`); a small `BudgetLedger` **port** with
atomic reservation is generic core. Scope hierarchies, reset periods, price lists, soft limits
and alerts are gateway / application policy and live in an adapter.

**Final API**

```text
interface BudgetLedger {
  reserve({ scopes, amountUsd, ttlMs, key }): Promise<BudgetReservation>   // atomic, all scopes or none
  commit(reservationId, actualUsd): Promise<void>
  release(reservationId): Promise<void>
  record({ scopes, amountUsd, key }): Promise<void>                         // nested usage, idempotent
  check(scopes): Promise<{ ok: boolean; scopes: BudgetScopeStatus[] }>
}
budget: { …, ledger?: { adapter, scopes: (ctx) => string[], estimate?, reservationTtlMs?, onError?: 'stop' | 'continue' } }
memoryBudgetLedger({ limits })   // eharness/storage/memory
budgetLedgerConformance(factory) // eharness/testing
estimateStepCostUsd(…)           // default estimate: input tokens × input price + (maxOutputTokens ?? 4 096) × output price
```

Before every model call (the wrap-up step included) the core reserves the estimate; after the step
it commits the actual cost (0 when the provider reported no usage); a refused reservation stops
the turn with `'cost-cap'` and `W_BUDGET` (`details.scope: 'ledger'`) **before** the call. Nested
usage (`ctx.turn.addUsage`, the compaction summarizer and flush, a manual `compact()`, the guard
of #2) is recorded with idempotent keys.

**Differences from the proposal**

- **No scope objects, no periods, no `soft`, no token limits in the port:** scopes are opaque
  strings the application defines; a period is a property of the adapter's row
  (`examples/postgres-budget-ledger.ts` uses monthly UTC periods).
- **No new stop reason** (`budget_exceeded` in the proposal): the existing `'cost-cap'` is used,
  with `details.scope: 'ledger'`.
- **`release` and `reserve` idempotency** were added to the proposal's `reserve/commit/check` so
  a crashed or retried step does not double-hold; a reservation of a dead process expires after
  `reservationTtlMs` (default `loop.turnTimeoutMs`, else 10 minutes).
- **Fails closed:** an unreachable ledger ends the turn with `'error'` (`EH_STORAGE`,
  `details.operation: 'budget-ledger'`) before the call; `onError: 'continue'` runs the step
  unreserved with `W_BUDGET_LEDGER_FAILED`. Commit and record failures are warnings.
- **The first reservation is the pre-turn check** (no separate call); an aborted step commits 0
  because AI SDK reports no usage for it (documented estimate limitation).
- The Postgres example sums open, unexpired reservation rows instead of keeping a counter that
  needs a sweep (a sweep over several scope rows can deadlock with reservations).
- Type-level: `W_BUDGET` `details.scope` gains `'ledger'`; `WarningCode` gains
  `W_BUDGET_LEDGER_FAILED`.

**What stays app policy:** scope naming and hierarchy (tenant / user / agent), calendar periods
and time zones, price lists beyond the `models` catalog, soft limits and alerts (raise them inside
`reserve` / `commit`), and the quota rules themselves. A gateway remains a good last line of
defence.

## #4 — Request-scoped client tools and page context

**Verdict:** generic, core, in a transport-agnostic form: tools declared per request without a
server `execute`, plus a per-request context block. It is the external-wait pattern (#1) with a
short fuse.

**Final API**

```text
handleChatRequest(session, body, {
  clientTools?: false | { allow?: string[] | (d) => boolean, maxTools? = 16, maxSchemaBytes? = 8_192, timeoutMs?, onTimeout? },
  pageContext?: false | { maxChars? = 4_000 },
})   // reads body.clientTools: { name, description?, inputSchema }[] and body.pageContext: { description, value }[]
SendOptions: clientTools, clientToolsOptions, pageContext, pageContextOptions   // server code, same validation
// texts PAGE_CONTEXT_PREAMBLE, CLIENT_TOOL_TIMED_OUT; helper neutralizeTags(); warning W_PAGE_CONTEXT_LIMITED
```

Declarations are validated all or nothing (name pattern, reserved names, collisions with any server
tool, schema type / bytes / depth, in-document `$ref` only, count, allow list) before anything is
stored; they become AI SDK tools without `execute` (risk `unknown`, so approval policy applies) and
sit after `tool_search`, before the output tool, sorted by name. Page context is a turn reminder
framed as data, capped, never stored. With `timeoutMs`, an unanswered call (tab closed) expires
through the external-wait machinery of #1.

**Differences from the proposal**

- The request field is **`pageContext`** (the proposal: `context`) and the feature is **opt-in**
  (`false` by default: the fields are ignored exactly as before 0.5).
- **No `client_` prefix:** the frontend keeps its own names; collisions are rejected instead.
- **Invalid page context is an error** (`EH_INVALID_INPUT`, `'page-context'`), consistent with
  declarations, not silently dropped.
- **The cache cost is documented, not hidden:** a changed declaration set busts the prefix and
  raises `W_CACHE_BUST` once per turn; deferring request tools behind `tool_search` is on the
  roadmap.
- **Page context is not persisted**, so a regenerated turn does not see the old page.
- Type-level: `ChatRequestBody` gains optional fields; `ChatRequestOptions` redefines
  `clientTools` / `pageContext` as opt-in objects; `PendingState.clientTools[]` entries gain
  optional `waitId`, `timeoutAt`, `onTimeout`, `result`; `EH_INVALID_INPUT` gains the reasons
  `'client-tools'`, `'page-context'`, `'request-context-with-steer-or-collect'`.

**What stays app policy:** which names a page may declare (the `allow` list), what the page tools
do, and what goes into page context (never secrets).

## #5 — Group-chat context engine

**Verdict:** generic in part, as a plugin. Mention gating, a pending history of what gating
skipped, and a bot-to-bot loop limit have prior art (OpenClaw, ElizaOS, AutoGen); they live in
bot/channel frameworks, so this is the least general item and ships as an opt-in subpath.

**Final API**

```text
import { groupChat, routeGroupMessage } from 'eharness/group'
const group = groupChat({ botId, botName?, requireMention? = true, mentionPatterns?, replyCountsAsMention? = true,
                          historyLimit? = 20, maxBotTurns? = { count: 3, windowMs: 60_000 }, allowBots? = false,
                          shouldRespond?, formatSpeaker? })
await routeGroupMessage(group, session, { text, author, mentionsBot, replyToBot, chatId, messageId })
  → { responded: true, run } | { responded: false, reason, messageId }
// kind group.message (model: 'omit'), metadata.group (needs acceptClientMetadata), GROUP_HISTORY_PREAMBLE, GROUP_SPEAKER_PREFIX
```

Gated-out messages are stored as the non-model kind `group.message`; the newest `historyLimit`
are merged, framed as data, into the next answering user message exactly once and in order.
Speaker identity travels in `metadata.group` plus a visible speaker line (no parallel message
type). Bot authors are ignored unless allowed; allowed bots count toward `maxBotTurns`, derived
from stored history (no counter), so it holds across instances.

**Differences from the proposal**

- **`shouldRespond` returns `'respond' | 'ignore' | 'default'`** (no `'stop'`; the anti-loop is a
  separate option), and receives `{ mentioned, session }` rather than a turn context, because it
  runs outside any turn.
- **A helper outside the turn, not an `input.submit` gate:** a block there would store nothing or
  an `eh.notice` per ignored message. `groupChat()` returns the plugin with a `route` method;
  `routeGroupMessage(group, session, message)` takes the plugin first.
- **History is merged into the answering message** (bounded, ADR-0011 holds) rather than
  projecting every `group.message` kind into context.
- **No rolling summary** in the plugin: it is the memory plugin's job, not group-specific.
- `botName` adds a default `@botName` mention pattern; the bot's own messages are dropped, not
  stored; file contents of gated messages are never stored (names and types only).
- **No core change** (`neutralizeTags` was lifted to core by #4 and the group wrapper keeps its
  output unchanged); no new type-level surface beyond the subpath.

**What stays app policy:** relevance thresholds, persona, "when the bot chimes in"
(`shouldRespond` is the hook), channel adapters (Telegram entities, Slack events: the plugin takes
`mentionsBot` / `replyToBot` as facts), sending the answer back, and summaries.

## #6 — OpenAPI → tools

**Verdict:** generic, plugin, not core: it depends on HTTP and authentication, and vendors warn
that curated tools beat mirrored APIs. The plugin is built to make curation the default.

**Final API**

```text
import { openApiTools, riskFromMethod } from 'eharness/openapi'
openApiTools(spec /* object or JSON string, OpenAPI 3.0 / 3.1 */, {
  name, baseUrl?, useSpecServers? = false, headers?: (ctx, op) => HeadersInit,
  include?, exclude?, names?, prefix? = `${name}_`, risk?: (op) => ToolRisk | undefined,
  maxTools? = 64, defer? = 'auto' (above 20), timeoutMs? = 30_000, maxResponseChars? = 50_000, schema?, fetch?,
}): ToolSource     // one tool per operation; input { path?, query?, headers?, body? }
```

**Differences from the proposal**

- **Named `openApiTools`**, returns a `ToolSource` (the proposal: `openApiToolset`).
- **The base URL is the application's.** `baseUrl` is required unless `useSpecServers: true`; the
  spec's `servers` are ignored by default (SSRF). Requests cannot leave the base URL (path
  values are encoded, `..` is rejected, redirects elsewhere are not followed).
- **Auth only through `headers(ctx, op)`**, per call, from `ctx.runtime`; credential headers
  (including API-key header names from `securitySchemes`) are blocked from model input; cookies
  are ignored.
- **Default risk from the method:** GET / HEAD / OPTIONS `'read'`, DELETE `'destructive'`, everything
  else `'write'` — not `'external'`, because internal APIs are common; the guide shows
  `risk: (op) => op.method === 'get' ? 'read' : 'external'` for third-party APIs.
- **Grouped input** (`{ path, query, headers, body }`) so parameter names cannot collide;
  response schemas are not used as `outputSchema`; JSON documents and JSON bodies only, local
  `$ref`s with a recursion guard; binary and streamed responses are not supported.
- Failures (HTTP, network, bad input) return as error strings the model can read.

**What stays app policy:** which operations the agent may call (`include` / `exclude`), the
credentials, the approval rules for the resulting risk, and the quality of the spec's
descriptions.

## #7 — Risk `'external'` and approval routing

**Verdict:** generic, core for the metadata (aligned with MCP annotations); routing is policy the
application injects through the approval chain that already existed.

**Final API**

```text
type ToolRisk = 'read' | 'write' | 'destructive' | 'external'
toolTraits(metadata) → { risk?, idempotent?, hints? }          // ToolTraits, ToolHints
tool({ metadata: { risk?, idempotent? } })                     // trusted app metadata
mcpServer({ risk?: ToolRisk | McpRiskFunction })               // eharness/mcp, trusted per server / per tool
approval: { risk: { external: 'user-approval' } }              // existing routing, one more key
// tool.approve event: risk?, idempotent?, hints?; ApprovalDecision and pending approvals: idempotent?
```

Rules: app metadata wins (it may be lower than the hints); MCP hints only **tighten**
(`destructiveHint: true` gives `'destructive'`, else `openWorldHint: true` gives `'external'`);
`readOnlyHint` and `idempotentHint` never lower a risk and `idempotent` comes only from app
metadata (it will drive retry decisions, so a server must not be able to loosen it).

**Differences from the proposal**

- **No new routing API** (`approvalPolicy(tool, args, actor)`): routing is the existing
  `approval.policy` / `approval.risk` / `tool.approve` chain with most-restrictive-wins; the guide
  documents the mapping in both directions (a table, no exported helper, since eharness exposes
  no MCP server).
- **No MCP spec defaults applied.** Defaulting `destructiveHint` / `openWorldHint` to true would
  make every unannotated MCP tool `'destructive'`, a large behaviour change in a minor; tools
  without hints stay `unknown` and the guide recommends `approval.risk: { unknown: 'user-approval' }`
  for untrusted servers.
- **One risk per tool**, derived precedence `destructive` > `external`.
- A `mcpServer({ risk })` function that returns an invalid value keeps the derived risk and logs
  (it runs at listing time, where throwing would drop the whole source).
- **Fix found while testing:** AI SDK re-validates an approved call (the `respond()` continuation)
  without `toolMetadata`, so the risk fell back to `unknown` and `approval.risk: { unknown:
  'denied' }` denied calls a person had just approved. The approval function now reads the
  traits from the tool itself.
- Type-level: `ToolRisk` gaining a member breaks exhaustive `switch` statements and
  `Record<ToolRisk, …>` objects.

**What stays app policy:** the routing table itself (which risk needs a person, per
organisation, per actor), which MCP servers are trusted, and per-tool `risk` / `idempotent`
declarations.

## #8 — Inbox poison items and dead-letter

**Verdict:** generic, core, because eharness owns a durable inbox port (0.4.0): bounded retries
with backoff and a dead-letter are standard queue practice, not business policy.

**Final API**

```text
inbox: { retry?: { maxAttempts?, backoff?: { type? = 'exponential', delayMs? = 1_000, maxDelayMs? = 60_000, jitter? = true },
                   nonRetryable? = (e) => e.code === 'EH_INVALID_INPUT' },
         onDeadLetter?: (item: DeadInboxItem) => void | Promise<void> }
InboxAdapter (all optional): release(ids, { delayMs?, uncount?, lastError? }), deadLetter(ids, info), redrive(ids),
                             listDead({ sessionId?, limit? }), stats() → { ready, claimed, delayed, dead }
InboxItemInput: availableAt?   InboxItem: lastError?
// SessionEvent 'inbox-dead'; warning W_INBOX_DEAD_LETTER; W_INBOX_FAILED operation 'deadLetter'
inboxAdapterConformance(factory, { requireRetry?, requireDeadLetter?, requireStats? })
```

Attempts are counted **at claim** (SQS receive-count semantics, so a crashing holder counts).
Deferrals (a turn of another instance runs, approvals are pending, a burst is not due) are
released with `uncount`, so a long foreign turn never consumes attempts. A failed attempt backs
off with `lastError`; an item past `maxAttempts`, or failing non-retryably (including a stored
input that no longer validates), is dead-lettered and reported through `onDeadLetter`, the
`inbox-dead` event and `W_INBOX_DEAD_LETTER`. `memoryInbox()` implements all of it;
`examples/postgres-inbox.ts` adds the columns with an in-place upgrade of a 0.4 table.

**Differences from the proposal**

- **Opt-in, unlimited by default** (the proposal had no default): a 0.4 adapter may not honour
  `uncount` and would dead-letter healthy items behind a long turn. The guide recommends
  `maxAttempts: 5` with an adapter that passes `requireRetry`.
- **Status vocabulary:** adapter-defined states ready / claimed / delayed / dead (counted by
  `stats()`), not `pending|leased|done|dead`.
- **No core `redrive()` wrapper:** redrive and `listDead` are adapter operations the guide wires
  to an admin route (avoids a second API surface). An adapter without `deadLetter` acks dead
  items after `onDeadLetter` ran ("bring a dead table").
- **`availableAt` on every item** was added (durable timers, used by the `wait-timeout` items of
  #1); a delayed item keeps its place in the session's head-of-line order, a timer holds nothing
  back, and `abort` items bypass both.
- **Drain-level failures** (reading the session's own state) are deferrals with the minimum
  backoff, so a storage outage never dead-letters a healthy backlog.
- Type-level: `SessionEvent` gains `inbox-dead`; `WarningCode` gains `W_INBOX_DEAD_LETTER`;
  custom `InboxAdapter`s keep compiling (new members are optional) but need the new
  `release` options and `availableAt` to use `maxAttempts` safely.

**What stays app policy:** the value of `maxAttempts`, who is paged and how (`onDeadLetter`), the
admin route that redrives, and the idempotency of side effects (mark safe tools
`metadata.idempotent`; give others a key such as the `waitId` or `inboxId`).

## Positioning note: AI SDK `@ai-sdk/harness`

AI SDK now ships an experimental `@ai-sdk/harness` (`HarnessAgent`, adapters for external agent
runtimes). eharness stays what it was: the library for **building** your own harness on AI SDK
primitives (ADR-0001). A `HarnessAgent` adapter, so an eharness agent can run behind it, remains a
roadmap row; nothing in 0.5.0 depends on `@ai-sdk/harness`.
