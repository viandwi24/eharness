# eharness 0.4.0 — results for BTeams

For: BTeams (first production user), answering the "eharness update proposal (target 0.4.0)"
items U1–U9. From: eharness maintainers. Status of this document: written before the 0.4.0
version PR; every item below is merged on `main` unless marked otherwise.

All changes are backward compatible in the 0.x sense: without new configuration, 0.3.x behaviour
is unchanged, with two deliberate exceptions called out in the changelog — the compaction thrash
stop (U8, default on) and the hardening fixes of the 0.3.1 audit (see
[Also in 0.4.0](#also-in-040)). Peer floors are raised to the locked, tested versions:
`ai@^7.0.127`, `zod@^3.25.76 || ^4.1.8`, optional `@ai-sdk/mcp@^2.0.66`. The signature blocks below are
summaries; the exact types are in the linked specs and in the package's `.d.ts`.

## U1 — `compaction.before` and the pre-compaction flush

**Final API**

```text
// a plugin hook (chainable)
'compaction.before'?(ctx: HarnessContext, e: CompactionBeforeEvent): Awaitable<CompactionBeforePatch | void>

interface CompactionBeforeEvent {
  messages: HarnessUIMessage[]   // the part that will be summarized (copies), not the kept tail
  tokens: number                 // calibrated estimate of the current context
  trigger: 'auto' | 'manual' | 'turn' | 'overflow'
}
interface CompactionBeforePatch {
  flush?: { prompt: string; tools?: string[]; maxSteps?: number /* 3 */; model?: LanguageModel }
}

// shortcut in the memory plugin (U5)
memory({ roots, flushOnCompaction: true | { prompt?: string } })
```

New exports: `CompactionBeforeEvent`, `CompactionBeforePatch`, `FlushPayload`,
`FLUSH_APPROVAL_DENIED`; `eharness/memory`: `MEMORY_FLUSH_PROMPT`, `MEMORY_FLUSH_TOOLS`. New
warning `W_COMPACTION_FLUSH_SKIPPED`.

**Differences from the proposal**

- **The flush is recorded.** The proposal said flush messages are not stored. The conversation
  the model sees is indeed unchanged (no flush message is ever projected), but the core stores one
  **model-invisible audit record**, core kind `eh.flush` (`FlushPayload`: trigger, merged prompt,
  model, steps, tool names and statuses, usage, cost, error — no tool inputs or outputs), saved
  before the compaction marker and streamed once as a transient `data-eh.flush` part. Reason:
  usage and cost appear in history and audits can see that a flush ran.
- **Usage source** is `'compaction-flush'` (summarizer usage is `'compaction'`); both count toward
  `TurnResult.usage`, `costUsd` and budgets (manual `compact()` charges the session).
- **Approvals are auto-denied** with `FLUSH_APPROVAL_DENIED` (reported to `approval.decided`,
  `by: 'policy'`); client tools are never offered. Nobody is asked mid-compaction.
- **`trigger` also has `'turn'`** (pre-turn compaction) next to `'auto'` (mid-turn), `'manual'`
  and `'overflow'`.
- **Context of the flush** is the whole current wire plus the prompt (not only the part being
  summarized): the model needs the recent tail to judge what matters. One extra call over a
  cached prefix.
- **Merge rules:** prompts joined with a blank line, tools unioned, `maxSteps` = max, `model` =
  last defined.
- **Order:** prune (U2) → skip rule → budget check → flush → summarizer. A used-up budget skips the
  compaction and the flush together; a flush that does not fit the flush model's window is
  skipped with `W_COMPACTION_FLUSH_SKIPPED` (for `'overflow'` only a `flush.model` with a larger
  window runs). A failing flush is `W_HOOK_FAILED` (`details.phase: 'flush'`) and compaction
  continues, as proposed.
- The flush does not count toward the running turn's steps or progress guard; its tool calls are
  not streamed to the UI.

## U2 — Prune stage

**Final API**

```text
import type { ToolResultPart } from 'ai'

compaction: {
  prune?: {
    keepTurns?: number     // default 2: completed turns (newest first) never pruned; the current turn never is
    minChars?: number      // default 2_000
    exclude?: string[]     // final tool names never pruned
    replaceWith?: (part: ToolResultPart) => string  // default TOOL_OUTPUT_PRUNED: `[output of <tool> pruned: <n> chars]`
  } | false
}
```

New exports: `PruneConfig`, `TOOL_OUTPUT_PRUNED`; `ContextStats.pruned?: { outputs, chars }`.

**Differences from the proposal**

- **Off by default** (`undefined` = off, `{}` = on with defaults), so 0.3 requests are unchanged
  byte for byte (golden test).
- **The summarizer transcript keeps the original outputs** (already capped at 2 000 characters by
  the transcript builder), not the placeholders: the summary is where information is condensed.
  The proposal had prune apply to the summarizer transcript too.
- **`replaceWith` receives AI SDK's `ToolResultPart`** (no parallel type) and must be pure; a throwing
  or non-string result falls back to the default placeholder.
- **Cache cost, documented:** the request is rebuilt at turn start, so when `keepTurns` slides the
  prefix changes **once per turn** at the oldest newly pruned output; within a turn it is stable.
- Errors, denials and provider-executed tool results are never pruned; only the `output` of a
  result is replaced (calls and pairs stay intact). Pruning inside the current long turn is out of
  scope (roadmap).

## U3 — Durable inbox

**Final API**

```text
interface InboxAdapter {
  enqueue(sessionId: string, item: InboxItemInput): Promise<string>        // durable before resolving
  claim(sessionId: string, owner: string, opts?: { limit?: number; claimTtlMs?: number }): Promise<InboxItem[]>
  ack(ids: string[]): Promise<void>
  release(ids: string[]): Promise<void>
  notify?(sessionId: string): Promise<void>
  subscribe?(sessionId: string, onNotify: () => void): () => void          // optional push (LISTEN/NOTIFY)
  pending?(opts?: { limit?: number }): Promise<string[]>                   // optional, for a sweeper
}
type InboxItemInput =
  | { kind: 'send'; mode: 'queue' | 'steer' | 'collect'; input: SerializedInput; collect?: CollectOptions; at: number }
  | { kind: 'wake'; messageId: string; at: number }
  | { kind: 'abort'; turnId?: string; reason?: string; at: number }
type InboxItem = InboxItemInput & { id: string; attempts: number }

defineHarnessAgent({
  storage: { messages, state, inbox },  // also SessionOptions.storage.inbox
  inbox: { pollMs?: number /* 2_000 */; claimTtlMs?: number /* recovery.staleMs */; collect?: CollectOptions },
})
session.enqueue(input: SendInput, opts?: { mode?: 'queue' | 'steer' | 'collect'; collect?: CollectOptions })
  : Promise<{ inboxId: string; target: 'local' | 'remote' }>
session.send(input, { ifBusy: 'collect', collect: { quietMs: 1_500, maxWaitMs: 10_000, maxItems: 20 } })
```

Shipped: `memoryInbox()` (`eharness/storage/memory`), `inboxAdapterConformance()`
(`eharness/testing`), a Postgres example (`FOR UPDATE SKIP LOCKED` + `LISTEN`/`NOTIFY`). New session
events `inbox-enqueued` / `inbox-drained`; warning `W_INBOX_FAILED`.

**Differences from the proposal**

- **Remote enqueue is an explicit method.** The proposal had `send()` in a non-holding process
  enqueue instead of failing with `EH_SESSION_BUSY` when `ifBusy` ≠ `reject`. A `send()` returns a
  run that streams the turn, which another process cannot provide (cross-process resumable streams
  are on the roadmap), so `send()` keeps its 0.3 semantics and the cross-process path is
  `session.enqueue(input, { mode })` → `{ inboxId, target }`. A chat route calls `enqueue()` when
  the turn runs elsewhere (or on the 409 busy answer) — example in the multi-instance and
  production guides. `enqueue()` takes no `SendOptions` (models, settings and runtime are not
  serializable); the holder's defaults apply.
- **`collect` also works in-process** (`send(…, { ifBusy: 'collect' })`, and `enqueue()` without an
  inbox), not only through the inbox.
- **Dedupe** uses the item id: user messages carry `metadata.eharness.inboxId` (merged ones
  `collected`), steers `data-eh.input.inboxId`, and the core keeps `state.core.inboxDelivered`
  (last 100 ids). The proposal's `deliveredIn` stays the field for injected kind messages.
- **Claim expiry** is per claim (`claimTtlMs`, default `recovery.staleMs`) instead of being tied to
  the heartbeat; the item types gained `id`/`attempts`, `wake.messageId` (the kind message was
  saved by the waking process) and `abort.turnId`.
- **`subscribe` and `pending`** are additional optional adapter methods (push notifications; app
  sweeper). The poll keeps running with `subscribe` as a safety net (`pollMs: 0` turns it off).
- Durable items are never dropped by `abort()` (released back to the inbox); a steer that misses the
  running turn becomes a queued turn at the next idle drain, and its `input.submit` hooks run again
  (`via: 'queue'`).

## U4 — Cross-process abort

**Final API**

```text
session.abort(reason?: string): void          // unchanged signature; now also reaches other instances
session.requestAbort(reason?: string): Promise<{ target: 'local' | 'remote' | 'idle' | 'unsupported' }>

defineHarnessAgent({ recovery: { staleMs?: number /* 120_000 */; abortPollMs?: number /* 2_000; 0 = off */ } | false })

// persisted
state.core.abortRequest?: { turnId: string; at: number; reason?: string; by?: string }
```

New exports: `AbortRequest`, `AbortRequestResult`; warning `W_ABORT_UNSUPPORTED`.

**Differences from the proposal**

- **`requestAbort()` added**, `abort()` unchanged (`void`; changing it to a promise would break
  implementers of `HarnessSession`). `abort()` calls it fire-and-forget when no local turn runs.
- **Requires `StateAdapter.setIf`** on the state path: without compare-and-set a blind write would
  clobber the owner's heartbeat or pending state, so the result is `'unsupported'` plus
  `W_ABORT_UNSUPPORTED` instead (only when a live foreign turn exists; an idle session answers
  `'idle'`). With an inbox, an `abort` item is used first (lower latency with `subscribe`).
- **Field `core.abortRequest`, turn-scoped** (`turnId`), instead of `core.abortRequestedAt`: a late
  Stop never aborts the next turn. It is the only `state.core` field another instance may write
  while a turn runs; owner writes use `setIf` and merge it on conflict.
- **Polling is bounded:** the owner reads state at most once per `abortPollMs` (at step ends and
  on a timer, so a long tool call is aborted mid-tool through its `abortSignal`). Latency ≤
  `abortPollMs` + one boundary. After 3 conflicting retries `requestAbort()` rejects with
  `EH_SESSION_BUSY` (no blind write; retry).

## U5 — Memory plugin

**Final API**

```text
import { executeMemoryCommand, memory } from 'eharness/memory'

memory({
  roots: (ctx: HarnessContext) => Awaitable<MemoryRoot[]>,   // { path, write?: boolean = false, label? }; resolved per turn
  pinned?: (ctx: HarnessContext) => Awaitable<string[]>,      // shown in the turn reminder
  maxPinnedChars?: number,                                     // 2_000 total
  maxFileChars?: number,                                       // 20_000 per file
  protocol?: string | false,                                   // MEMORY_PROTOCOL, static instruction
  tool?: (execute: MemoryExecutor) => Tool,                    // app-supplied single tool named `memory`
  onWrite?: (e: MemoryWriteEvent, ctx: HarnessContext) => Awaitable<void>,
  flushOnCompaction?: boolean | { prompt?: string },           // U1, default false
})
// tools: memory_view, memory_create, memory_str_replace, memory_insert, memory_delete, memory_rename
// FileSystem.move?(from, to, { ifVersion? }): Promise<MoveResult>   (optional; memoryFs implements it)
```

Exports: `memory`, `executeMemoryCommand`, `MEMORY_PROTOCOL`, `PINNED_PREAMBLE`, `MEMORY_TOOLS`,
`MEMORY_FLUSH_PROMPT`, `MEMORY_FLUSH_TOOLS`, `DEFAULT_MAX_FILE_CHARS`, `DEFAULT_MAX_PINNED_CHARS`,
types `MemoryCommand`, `MemoryRoot`, `MemoryWriteEvent`, `MemoryOptions`, `MemoryExecutor`.

**Differences from the proposal**

- **`tool` instead of `providerTool: boolean`.** eharness takes no dependency on
  `@ai-sdk/anthropic` (no new runtime dependencies without an ADR). The application builds the
  provider tool from the exported executor:
  `memory({ roots, tool: (execute) => anthropic.tools.memory_20250818({ execute }) })`.
- **`onWrite` option instead of a `memory.write` hook.** Core hook names are a closed set; the
  callback has the same event (`op`, `path`, `to?`, `before?`, `after?` with version and size,
  `toolCallId?`); its errors are `W_HOOK_FAILED` and never change the tool result.
- **Roots are resolved per turn** (so per-turn `runtime` is honoured); pinned files outside the
  roots are skipped. **Pinned files go into the turn reminder** (`refresh: 'turn'`), not the
  system prompt: tool definitions and the static instructions are byte-identical for every user.
- `flushOnCompaction` shipped on top of U1 (offers `memory_view`, `memory_create`,
  `memory_str_replace`, `memory_insert`; never delete/rename; skipped when no root is writable).
- Contract details: `create` on an existing file is an error (no overwrite); `str_replace` is
  exact (the Anthropic contract, no whitespace-tolerant matching); directories cannot be deleted
  or renamed; ancestors of roots are outside the roots.

## U7 — Skill versions

**Final API**

```text
interface SkillMeta { name: string; description: string; version?: string; meta?: Record<string, unknown> }
// also Skill, SkillDoc; SKILL.md frontmatter `version: 2.1.0` (read as a string: `1.0` stays "1.0")
'skill.load'?(ctx, e: { skill: SkillDoc; source: string; location?; version?: string })
```

**Differences from the proposal**

- **Shown in `load_skill`, not in the skills index:** the index stays cache-stable when only
  versions change. `load_skill` prints a `version:` line right after `description`.
- Validated (1–64 printable characters); an invalid version makes the skill invalid
  (`W_INVALID_SKILL` / `EH_CONFIG_INVALID`). `skillSourceConformance` checks that `version`
  survives `list()` and `load()` (opt out with `{ version: false }`).

## U8 — Compaction thrash detection

**Final API**

```text
compaction: { thrash?: { withinSteps?: number /* 2 */ } | false }
// StopReason gains 'context-thrash'; warning W_CONTEXT_THRASH; eh.notice code EH_CONTEXT_THRASH
```

**Differences from the proposal**

- Same semantics; the knob is `compaction.thrash` and it is **on by default** (a behaviour change
  in a minor, allowed in 0.x and called out in the changelog): repeated compaction in one turn
  burns money without progress. `thrash: false` restores 0.3 behaviour.
- `turn.beforeEnd` does not run for `'context-thrash'`; an `eh.notice` (warning) is stored so UIs
  can show why the turn stopped. Exhaustive `switch` statements over `StopReason` must add the
  case.

## U9 — Production-patterns guide

`docs/guides/production-patterns.md`, sections:

1. **Ephemeral context** — a table of every place context can go (stored or not, cached or
   not), `refresh: 'turn'` instructions for live data, `step.prepare` reminders for retrieved
   memories, and the warning that `input.submit { context }` and `step.end { context }` are
   **stored**.
2. **Episodic and long-term memory** — `compaction.after({ marker })` → `CompactionPayload.summary`
   into your own store; the memory plugin with `flushOnCompaction` (U1, U5).
3. **Background events** — `messageKinds` + `inject(kind, data, { deliver, wake })`, delivery
   table, agent-to-agent messages.
4. **Several instances** — `SessionLock`, `setIf`, `lastId`, `recovery.staleMs`, cross-process
   abort (U4), inbox (U3), `ifBusy: 'wait'` / `idle()` and the 409 route with an ownership check.
5. **Scheduling and heartbeats** — the scheduler is the application's; `inject(…, { wake: true })`
   and the **silent OK** pattern (`nothing_to_report` tool + `step.end` stop →
   `plugin:heartbeat:silent`).
6. **Skills from a database** — a custom `SkillSource` with `version` (U7) and a `skill.load`
   audit hook.
7. **Pipeline workers and tool-heavy agents** — structured output (U6, pending) and prune (U2).
8. **Security** — design-level risks with default and required action: session ownership
   (including the resume GET route), `runtime` shared per live session, per-session budgets,
   exact-prefix path checks, shared evicted tool outputs, agent-written skills
   (`hideSkillsRoot: false`), session-wide grants, logs and error texts, provider-fetched URLs,
   and what the core already guarantees.

**Differences from the proposal:** none in scope; the guide adds the pipeline/prune and security
sections and an offline example ([`background-events.ts`](../../examples/background-events.ts)).
One finding while writing it: inside a `refresh: 'turn'` instruction `ctx.turn.input` is not yet
set (instructions are resolved before the input is normalized), so retrieval that depends on the
user's message belongs in `step.prepare` — the guide shows that pattern.

## Also in 0.4.0

Hardening fixes of the 0.3.1 audit that matter for BTeams (full list: changelog):

- **409 instead of a throw:** `handleChatRequest` never throws `EH_SESSION_BUSY`; it returns a
  failed run whose `toResponse()` answers **409** `{ error: { code, message } }`. The stream of a
  turn now ends only after the turn is persisted, so a client that saw `finish` can send at once.
- **`ifBusy: 'wait'`** for `send()` and `respond()` (FIFO, honours `abortSignal`) and
  **`session.idle()`**.
- **Stricter adapter conformance:** `messageAdapterConformance` now fails adapters that merge on
  upsert, compare `fromId` by exact match, or mishandle `beforeId` without `limit` — re-run it
  against your Postgres adapter.
- **`inputFiles`:** user file URLs are limited to `['data:', 'https:']` and 20 MB `data:` URLs by
  default (`EH_INVALID_INPUT` otherwise); expired files of earlier turns no longer break later
  turns (`FILE_UNAVAILABLE`).
- **`toolErrorText`:** map thrown tool errors to safe text (identical in UI, storage and model
  wire); provider error texts are redacted and capped.
- Summarizer usage counts toward usage, cost and budgets; out-of-range options throw
  `EH_CONFIG_INVALID`; `handleChatRequest(…, { actor })`; `read_file` `charOffset`; a safe `grep`
  regex subset.
